#### 分工
这个时代，备战秋招基本上不用写具体的代码了，因此项目推进当中不关心具体的代码，如果项目中涉及一些核心算法和逻辑值得手写，或者部分代码片段值得看懂阅读，不在项目推进中进行，在“代码练习”板块的模块练习当中进行。

项目推进过程中，codex帮我推进代码，我负责理解链路、模块、输入输出、测试、失败排查和核心逻辑。

#### 分阶段
项目推进分为几个大阶段。实际推进当中，大阶段需要分为多个小阶段，每次codex推进一个小阶段。小阶段方案不在一开始就静态写出来，要在实际推进当中，每完成一个小阶段后，总结当前情况，再写下一个小阶段方案。

开始一个大阶段之前，我会让网页版GPT阅读github仓库理解项目背景和进度，然后帮我写该大阶段的各个小阶段推进方案，要求展开写清楚按照哪些小阶段推进，每个小阶段要达成什么；

每当一个大阶段完成，我会从面向面试的角度先理解清楚这个大阶段做了些什么，然后再进入下一个大阶段。每个小阶段和每个大阶段要有验收标准。

#### 文档
两个项目都以 README 作为唯一总入口。

README 必须包括：

```text
1. 项目定位和顶层设计
2. 解决的问题
3. 总体架构图或文本链路图
4. 核心模块职责
5. 快速启动
6. Demo 输入输出
7. 测试命令
8. 关键数据与产物结果
9. 关键设计取舍
10. 任务队列
11. 版本变化与进度记录
12. 教材性质的“从项目起点到现在，做了哪些工作，目的和实现方式，遇到哪些问题和如何排查。”
```

不建议单独拆太多文档。

只有当具体的实现细节过长，或者一些特定任务的产物与结果，才拆到 细分docs。

文档原则：

```text
README 负责讲完整主线。
docs 只负责放过长细节。
不要让 README 变成目录索引。
不要让 docs 变成无人维护的碎片仓库。
```

在项目推进过程中，理解项目主要是宏观的；等项目完成后，在秋招冲刺的时候，才是更深入去加强理解。需要协调好“推进过程中兼顾速度与合适的理解细度与深度”和“秋招前冲刺再深挖具体的理解”。我在推进过程中，不能把理解项目分得过于细，以免妨碍推进速度；同时又不能理解得过于宽泛，以免深究就露馅。

项目推进的唯一目的，就是面对秋招的面试，能够口述链路、架构、模块，能够应对提问并且将回答延申，能够应对回答后的追问。

#### 5.3.2 模型与 artifact 来源

项目1支持两类模型来源。

第一类：旧项目中的 YOLO / NEU-DET 产物。

```text
作用：作为最稳定的 C++ Runtime baseline。
优点：输出结构简单，适合快速打通 C++ preprocess / infer / postprocess / NMS / benchmark。
定位：工程闭环基线，不再包装成项目最大创新点。
```

第二类：`paper_detect` 的训练测 artifact。

```text
作用：作为项目1的高质量研究侧 artifact 输入，增强项目1的模型来源、实验可信度和工业缺陷检测深度。
定位：paper_detect 负责训练、验证、消融、official test、result card；项目1负责读取或迁移 artifact，并在工程侧做部署、benchmark、事件输出和面试展示。
```

`paper_detect` 当前可传给项目1的核心 artifact 口径：

```text
D-FINE-S + DeepPCB 是强 baseline。
D003 是 D010 之前的 adaptive prior input adapter reference / proposed ancestor / 消融锚点。
D010 Template-Counterfactual Defect Denoising 是当前 proposed method。
D010 保持 D003 inference path，不引入 D009 feature-pyramid injection；核心新增在训练期 template-counterfactual erase/replay 样本。
D010 已完成 preflight、runtime diagnostic、1 epoch smoke、probe20、120e formal validation、best-checkpoint per-class validation、official test。
D010 formal validation AP50-95 = 0.847057。
D010 official test AP50-95 = 0.830385。
D010 相对 D003 在 formal 和 official-test 的 6 个类别 delta 全部为正。
D010A erase-only 与 D010B replay-only 都高于 D003，但低于 full D010，支持 erase + replay 组合。
```

项目1对 `paper_detect` artifact 的接入分三层，不一次性硬吃完：

```text
L0：结果卡接入
把 D010 / D003 / D001 的 result card、metrics table、per-class delta、定性图和配置说明同步到项目1的 artifacts/paper_detect/ 下；README 说明项目1可以消费这些训练测产物，但不在项目1中重训。

L1：部署契约接入
为 paper_detect 产物定义 model_artifact.yaml，包括 model_family、input_size、class_names、preprocess、postprocess_type、metric_summary、artifact_path、source_commit、result_card_path。

L2：ONNX / Runtime 接入
当 D010 或 D-FINE-S ONNX artifact 稳定后，再通过 DfinePostProcessor 或统一 DetectorPostProcessor 接入 C++ Runtime；如果 D-FINE 后处理复杂，则先保留 Python reference 对齐，再逐步迁移 C++。
```

```text
定义 SQLAlchemy ORM 表结构。

封装数据库读写，不写业务决策。

service
处理业务规则、事务边界、状态流转和审计写入。

agent
只放 AgentRunService、orchestrator、tools、tool_registry、policy、tracing、eval。

core
配置、日志、数据库连接、错误类型、权限工具。
```

Redis 必须有真实用途，不为堆技术栈而存在：

```text
agent_run lock：同一个 incident 同一时间只能启动一个诊断。
rate limit：限制 Agent 诊断调用频率。
短期缓存：缓存 knowledge search 或 incident history 查询结果。
```


#### 5.4.4 LangChain / LangGraph / RAG 分层设计  
  
项目2的 Agent 不写成“调一次大模型得到答案”，而拆成四层。

- 第一层：后端业务底座  
```
FastAPI / PostgreSQL / Redis / SQLAlchemy / Alembic  
负责 asset、inference_event、incident、ticket、knowledge_document、audit_log、agent_run 等业务对象。  
```
  
- 第二层：LangChain Agent Harness  
```
负责模型接入、prompt 模板、tool schema、tool calling、structured output 和 retriever tool 封装。  
这一层解决“LLM 如何以受控方式调用业务工具”的问题。  
```
  
- 第三层：LangGraph Workflow  
```
负责把 Agent 诊断过程编排成 StateGraph：  
load_incident  
→ retrieve_context  
→ call_tools  
→ assess_risk  
→ draft_ticket  
→ human_review  
→ finalize  

低风险路径可以直接生成 ticket_draft。  
高风险路径必须进入 human_review。  
工具调用失败或证据不足时进入 fallback。  
```
  
- 第四层：RAG Knowledge Layer  
```
knowledge_document  
→ chunk  
→ embedding  
→ vector store / keyword fallback  
→ retriever tool  
→ retrieved_chunks  
→ citation  
→ evidence insufficient fallback  
→ RAG eval
```


这个分层的面试口径：

```
LangChain 负责 agent harness 和工具抽象；LangGraph 负责可控 workflow 和状态机编排；RAG 负责证据检索和引用；FastAPI + PostgreSQL + Redis 负责业务状态、持久化、审计和可复现运行。
```

项目2不追求复杂多 Agent，而是把单 Agent 的工具调用、检索证据、状态流转、人审、审计和 eval 做扎实。


#### 5.4.5 Agent 边界

Agent 的职责：

```text
读取 incident、asset、model artifact、inference event、历史工单和知识库。
调用受控 tools。
生成诊断建议、风险等级、处理步骤和工单草稿。
对证据不足的情况返回“不足以判断”。
把所有 tool call、trace、audit 和 eval 记录下来。
```

Agent 不允许：

```text
不直接修改资产状态。
不直接关闭 incident。
不直接创建或推进正式 ticket，除非经过人工确认接口。
不绕过 service/repository 直接写库。
不在没有引用证据时编造原因。
不做多 Agent 炫技。
```

推荐 Agent 主链路：

```text
POST /agent/diagnose-incident
→ AgentRunService.create_run
→ load_incident
→ retrieve_context
→ call_tools
→ assess_risk
→ draft_ticket
→ human_review_if_needed
→ finalize
→ write agent_steps / agent_tool_calls / audit_logs
→ run eval checks
```

推荐 tools：

```text
query_asset
query_incident_history
search_knowledge_base
query_model_artifact
query_inference_event
risk_assessment
draft_ticket
submit_for_human_approval
```

执行策略：

```text
执行策略：

第一阶段用 FakeOrchestrator / rule-based orchestrator 跑通 AgentRunService、tool registry、agent_steps、agent_tool_calls、audit_logs 和 eval，不依赖真实 LLM。

第二阶段接入 LangChain Agent Harness，把 query_asset、query_incident_history、search_knowledge_base、query_model_artifact、query_inference_event、risk_assessment、draft_ticket 封装成受控 tools，并约束 structured output。

第三阶段把 FakeOrchestrator 替换为 LangGraph StateGraph。LangGraph 是 v1.0 正式展示版本的一部分，不是可选项。

替换 LangGraph 时，只替换 orchestrator 内部实现，不重写 router、service、repository、tool registry 和数据库表。
```

### 6.1 推进总原则

项目推进只写大阶段，不在路线里静态写定小阶段。每进入一个大阶段前，再让网页版 GPT / Codex 阅读：

```text

```

然后再动态拆成多个小阶段。每个小阶段只做一个清晰任务，完成后必须输出：

```text

3. 每个文件在链路中的作用
4. 关键入口函数是什么
5. 如何运行

```


```text

7 月下旬到 8 月上旬：项目2主攻，项目1补优化和接 artifact。
```

```text
→ retrieved_chunks：document_id / chunk_id / score / snippet
→ call_tools
→ assess_risk
→ draft_ticket
→ citation check
→ evidence insufficient fallback
→ human approval interrupt
→ finalize
→ audit log
→ golden cases eval
```

项目2分主题推进：

```text
1. LangGraph StateGraph：把 FakeOrchestrator 替换为正式 LangGraphOrchestrator。
2. Graph nodes：load_incident、retrieve_context、call_tools、assess_risk、draft_ticket、human_review、finalize。
3. Graph edges：低风险路径直接 draft_ticket，高风险路径进入 human_review，证据不足路径进入 fallback。
4. RAG indexing：knowledge_document → chunk → embedding → vector store / keyword fallback。
5. RAG retrieval：search_knowledge_base 返回 document_id、chunk_id、score、snippet。
6. RAG citation：Agent 输出 diagnosis 和 ticket_draft 必须引用 retrieved_chunks。
7. evidence insufficient：检索不到证据时不编造，返回“不足以判断”。
8. human-in-the-loop：高风险 ticket_draft 必须 pending_approval。
9. audit：记录 Agent 诊断、tool call、ticket draft、人审动作。
10. eval：建立 10 个 golden cases，检查引用、越权、胡编、risk_level、ticket_draft 和 fallback 是否正确。
```

```text
项目2有 10 个 golden cases 和 eval 输出。
```
