## 推进规则

>时间安排：周一到周五，每天下班后花3小时推进项目；周六周日每天8小时。

#### 分工

这个时代，AI编程越来越重要，因此项目推进当中不在具体的代码花过多时间，而是主要把时间放在针对面试的理解和问答上；当然不是说完全不管具体代码，将项目当中的的一些值得手写的核心算法和逻辑，划分为几个模块，放在“代码练习”板块的模块练习当中进行。

项目推进过程中，codex帮我推进代码，我负责理解架构、链路、模块、数据流动、输入输出、测试、失败排查和核心逻辑。

注意：我要求Codex推进项目不是单纯做项目，而是教学级的推进，走一步等一步，确保我学会以及理解到能够应对面试的程度；同时一定要抓重点，让我理解面试中最可能考察的核心逻辑。

#### 分阶段

项目推进分为几个大阶段。实际推进当中，大阶段需要分为多个小阶段，每次让codex推进一个小阶段，暂停，我来理解以及通过验收，再进入下一个小阶段。

小阶段方案不在一开始就静态写出来，要在实际推进当中根据情况去写。开始一个大阶段之前，我会让CODEX阅读仓库，理解项目背景和进度，然后帮我写该大阶段的各个小阶段推进方案，要求展开写清楚按照哪些小阶段推进，每个小阶段要达成什么；每完成一个大阶段后，我会从面向面试的角度先理解清楚这个大阶段做了些什么，然后再进入下一个大阶段，并且写下一个大阶段内部的小阶段方案。每个小阶段和每个大阶段要有验收标准。

#### 文档

项目都以 README 作为唯一总入口。

README 必须包括：

```text
1. 项目定位、顶层设计、解决的问题
2. 总体架构图或文本链路图、各个模块职责
3. 快速启动入口、Demo 输入输出、测试命令
4. 各阶段记录、版本变化记录、任务队列、当前进度记录
5. 关键数据与产物结果
6. 关键核心设计以及具体细节
7. 教材性质的总览“从项目起点到现在，做了哪些工作，目的和实现方式，遇到哪些问题和如何排查。”
```

不建议单独拆太多文档。

只有当具体的实现细节过长，或者一些特定任务的产物与结果，才拆到细分docs。

文档原则：

```text
README 负责讲完整主线。
docs 只负责放过长细节。
不要让 README 变成目录索引。
不要让 docs 变成无人维护的碎片仓库。
```

#### 每阶段CODEX输出

每次让codex推进一小阶段后，都要求它输出以下9个部分：

```
1. 本次总览上做了什么？
2. 本次推进涉及到哪些模块的更新/添加，为什么这么设计？
3. 修改了哪些文件，文件树结构经过了怎样的变化，为什么要这么改，修改/增加的各个文件在链路中的作用？
4. 如果人工手动推进，这一小阶段的具体工作的流程是怎样？
5. 关键入口函数是什么，核心类/函数是什么？输入输出分别是什么？用宏观伪代码描述最核心的逻辑。
6. 如何运行，如何测试，出错如何排查？如何完成一些微调、修改、自定义？
7. 给本次推进，写几个验收问题以及追问，确保我从面试层面理解透彻。
8. 哪几段代码（写清楚哪个文件哪几行）是这一小阶段当中，如果面试的时候问具体实现细节，最可能被问到的？换句话说，哪些核心逻辑建议我放在“代码练习的模块板块”去手写或具体理解。
9. 更新README，做好日志，记清楚当前进度，记录关键数据、路径、文件函数类等。
```


#### 理解的细度/深度/颗粒度

在项目推进过程中，理解项目主要是宏观的；等项目完成后，在秋招冲刺的时候，才是更深入去加强理解。需要协调好“推进过程中兼顾速度与合适的理解细度与深度”和“秋招前冲刺再深挖具体的理解”。我在推进过程中，不能把理解项目分得过于细，以免妨碍推进速度；同时又不能理解得过于宽泛，以免深究就露馅。

项目推进的唯一目的，就是面对秋招的面试，能够口述链路、架构、模块，能够应对提问并且将回答延申，能够应对回答后的追问。

## 项目顶层设计

- 定位：工业视觉边缘 AI Runtime 与 C++ 工程化系统
```
把一个公开工业视觉模型 artifact 转换为可配置、可运行、可测试、可比较和可复现的 C++ 推理软件，部署到端侧平台进行边缘计算。
```

- P0 主线：

```
1. C++17/CMake 多 target 工程，头源分离和明确依赖。
2. Config 与 artifact schema 校验：模型、输入尺寸、类别、阈值、前后处理类型。
3. OpenCV 前处理：letterbox、BGR/RGB、normalize、HWC→CHW。
4. ONNX Runtime C++ session：name/shape/dtype/provider 检查与 RAII。
5. YOLO 或一个稳定模型的 decode、score filter、NMS、坐标还原。
6. JSON 与可视化输出，固定 sample 和可复现命令。
7. Python/ONNX/C++ 一致性：固定样本、容差、检测数量、类别和坐标误差。
8. Benchmark：warmup、repeat、P50/P95、throughput、分段耗时、峰值内存或 RSS。
9. 量化与验证 INT8 PTQ / QAT
10. GTest：配置、非正方形 letterbox、颜色/布局、NMS、坐标反算、非法输入。
11. 故障注入：模型不存在、shape/dtype 错误、类别不匹配、空输出、损坏图片。
12. README：定位、架构、Quick Start、测试、结果、限制、复现实验环境。
```

- P1 工程深度扩展：

```
A. C++ 产品/系统软件：目录批处理 + 有界队列/worker + backpressure + clean shutdown，比较单线程与并发吞吐。

B. 推理部署：TensorRT/Jetson/ARM 真实部署，比较正确性、延迟、内存和温度；没有硬件就不做。

C. EDA/Windows/产品 UI：Qt 结果查看器；仅在多个高优先 JD 要求 Qt 时做。

D. 服务化/模型平台：gRPC 或 Triton；仅在多个高优先 JD 要求时做。

E. D010 模型artifact接入
```

- 模型 artifact 规则：

```
- 旧 YOLO/NEU-DET 可作为稳定 P0 baseline。
- 第二模型 `paper_detect`/D010 是我的论文实验方法，基于D-FINE-S （变体RT-DETR）；数据集为DeepPCB。
- `paper_detect`/D010 只有在导出稳定 ONNX、完成实际 Runtime 接入和一致性验证后，才进入项目结果。（结果卡->部署契约->ONNX Runtime接入）
```

- artifact 口径：

```
D-FINE-S + DeepPCB 是强 baseline。
D003 是 D010 之前的 adaptive prior input adapter reference / proposed ancestor / 消融锚点。
D010 Template-Counterfactual Defect Denoising 是当前 proposed method。
D010 保持 D003 inference path，不引入 D009 feature-pyramid injection；核心新增在训练期 template-counterfactual erase/replay 样本。
D010 已完成 preflight、runtime diagnostic、1 epoch smoke、probe20、120e formal validation、best-checkpoint per-class validation、official test。
D010 formal validation AP50-95 = 0.847057。
D010 official test AP50-95 = 0.830385。
D010 相对 D003 在 formal 和 official-test 的 6 个类别 delta 全部为正。
D010A erase-only 与 D010B replay-only 都高于 D003，但低于 full D010，支持 erase + replay 组合。
```

- 结果表至少包含：

```text
机器与 OS/编译器/构建类型
模型、输入尺寸、数据集/样本数
正确性标准和容差
preprocess/infer/postprocess/end-to-end P50/P95
throughput 与内存
单线程/扩展方案比较（若完成）
失败案例与结论
```
